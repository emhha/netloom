# MITM 流量性能

## 如何复现

```sh
go test ./traffic -run '^$' -bench '^BenchmarkMITMLoad$' -benchtime=1000x -count=3 -cpu=4 -timeout=2m
```

[基准实现](../traffic/mitm_benchmark_test.go) 使用本机 HTTPS 源站和解密式 MITM。八个客户端 worker 发出共 1,000 次请求，每次完整读取响应。每十次请求包含八次访问同一份 gzip JS、一次用不同查询参数请求同一份 gzip JS、一次读取短 JSON。JS 解压后为 64 KiB，源站预先压缩。所有模式使用同一组请求和两段 TLS。异步分析沿用默认的一名 worker、32 个等待项和每方向 128 KiB 的采集上限。

| 模式 | 分析配置 |
| --- | --- |
| `forward-only` | 直接转发的 MITM Backend |
| `metadata-cache` | `infoextract`，默认按元数据去重 |
| `body-hash-cache` | `infoextract`，按正文哈希去重 |
| `both-plugins` | 默认 `infoextract` 加 `serialization` |
| `slow-plugin` | 默认 `infoextract` 加每次等待 2 ms 的模拟插件 |

`forward_req/s` 和 p95/p99 从客户端实际读完整响应计算，包含初次建立连接的开销。分析排空在计时结束后进行。`reports_%` 和 `dropped_%` 使用请求总数作分母，`body_hits_%` 使用已交付的报告数作分母。基准检查每个响应的状态及正文长度，并核对交付数加丢弃数等于请求数。失败报告会使该轮基准失败。

这组测试是固定并发的本机负载，不能用于估算外网代理容量、长时间峰值内存或真实浏览器站点的表现。每个模式单独测量，默认验证不会执行基准。

## 2026-11-19 测量结果

Go 1.26.3 linux/amd64，AMD Ryzen 7 6800H，`-cpu=4`。先按上文运行每模式三轮 1,000 次请求，再将 `-benchtime` 改为 `10000x`，每模式重复三轮。两种规模均通过所有 HTTP 转发和报告计数断言。以下是 10,000 次请求的三轮中位数，分别对每列取中位数。

| 模式 | 转发请求/秒 | p95 | p99 | 分析报告 | 分析丢弃 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 只转发 | 13,008 | 1.64 ms | 2.72 ms | — | — |
| 元数据去重 | 7,652 | 2.62 ms | 4.10 ms | 20.23% | 79.77% |
| 正文哈希去重 | 7,703 | 2.57 ms | 4.27 ms | 18.57% | 81.43% |
| 两个插件 | 8,234 | 2.33 ms | 3.85 ms | 1.17% | 98.83% |
| 模拟慢插件 | 9,466 | 2.22 ms | 3.61 ms | 3.84% | 96.16% |

仅开启信息提取时，约 90% 的已交付报告命中正文去重，但报告覆盖率约为五分之一。两种键的转发吞吐相近。这组基准不能把差异归因到具体阶段，因为两种模式都采集副本和解码 gzip。两个插件模式和慢插件模式仍保持转发，大量报告在队列满时被丢弃。因此应同时看吞吐和报告覆盖率。

如果目标是提高全量分析的交付率，先用真实目标负载确定最低覆盖率，再评估分析并发以及 gzip 解码前能否安全跳过已知输入。仅扩大队列可以容纳更长的突发，持续负载超过分析速度时仍会丢弃报告。这些数据未包含峰值内存和 CPU profile。
